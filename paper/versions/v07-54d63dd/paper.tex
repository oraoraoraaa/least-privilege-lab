\begin{center}
{\LARGE\bfseries Which SQL Migrations Need Rehearsal?\par}
\vspace{4pt}
{\large Field forecasts, preparation errors and recipient access\par}
\vspace{6pt}
{\small Empirical study \enspace$\cdot$\enspace November 2026}
\end{center}

\begin{abstract}
An unchanged query can acquire access to private data after a rebuild. We compare preparing old SQL on a planned schema with forecasts made from schema changes and query syntax. A selective rehearsal rule reproduced every added-field list in five discovery histories using seven native rehearsals. We froze the rule before testing three further project histories. Across 425 old-query comparisons it selected no rehearsals, disagreed with full rehearsal four times, and predicted the next fields correctly in all four disagreements. It supplied none of the 18 native preparation errors. Cold syntax analysis took longer than native preparation on both machines. Extending the SQLite model recovered 148 previously incomplete database transitions. For these, full-column coverage and broad table diff installed identical policies, admitting the entire next catalog in 126 transitions. An Android wallet export demonstrates why an internal query's required reads and a recipient's permitted fields demand separate decisions.
\end{abstract}

\section{When the reviewer sees the change}
Mihon's \code{getMangaById} kept its source wildcard across releases v0.18.0 and v0.19.0. Rebuilding it against the new schema added \code{mangas.notes} to the explicit SQL in the shipped APK. We extracted both literals and ran them on the same database containing a known note. The old grant set admitted the old literal and denied the new one. Granting the notes field let the new literal return the fixture note. The old literal still omitted it. The repository method maps the result into the object used by the notes screen~\cite{mihon}.

A reviewer who sees planned DDL early can ask which currently known queries acquire dependencies or fail to prepare. At release review the new SQL can be measured directly. FeedFlow illustrates the timing difference. In February 2024 it added a bookmark field. A diff flagged the old unread-count query because it touched the table. The query remained unchanged and acquired no read. In February 2025 a drawer-badge change edited that same query to read the existing bookmark field. At that later transition all four early forecasts were empty~\cite{feedstages}. Granting the field at the first alert would have been premature for this query. Measuring the replacement at the second review exposes its requirement. In the fresh cohort we found no entirely unused new column later read by a surviving name before another DDL change on a continuously complete catalog. The FeedFlow case illustrates a caller-specific opportunity. These commits establish when source was available. Whether reviewers acted on a forecast is unknown.

Static schema-impact analysis traces dependencies through application queries and database objects~\cite{maule,hecataeus}. We measure the added authorization requests, the native diagnostics from preparing the old program, and the decisions produced by installed policies. Our syntax baseline examines projection wildcards. A semantic dependency analyzer for both versions of every view is outside the comparison.

\section{Why try selective rehearsal?}
The first migration evaluation used Tivi and Mihon for development, then froze four forecasts before testing five further SQLDelight projects. The latter five are the discovery cohort for the selective rule in this paper. We followed adjacent changes to declared databases across 2023--2025, including query-only edits. Named reads were matched by file stem and query label. An expansion is a supported surviving name whose next set of SQLite reads contains a resource absent from its old set. Exact prediction requires equality with the entire added set. Each repeated name at a later transition counts again.

Each predictor receives old SQL and the planned schema. Table diff names additions on relations previously read. Coverage restricts additions to relations on which the old footprint contained every declared column. Stars follows projected wildcards in old SQL and old view definitions. It resolves aliases and distinguishes a projection from \code{COUNT(*)}. Full rehearsal prepares the old SQL on planned definitions and records additional native reads. A preparation error predicts an empty added set and supplies a diagnostic. SQLite authorization observes projection, predicates, joins, views and underlying relations~\cite{sqlite}. Availability below counts distinct named statements per transition without traffic weights.

Table diff exactly recovered every one of rehearsal's 42 exact predictions. No correctly predicted rehearsal field was missing from the diff. Diff also proposed 178 extra query--field instances against zero for rehearsal. Of the 157 expansions, 119 involved edited SQL. All four forecasts missed the exact set on the 28 edited queries whose new reads were confined to existing resources. For all 38 unchanged expanding queries rehearsal was exact. Neither unchanged text nor an old footprint identifies all future developer edits.

Two FeedFlow callers inherited a new filter on \code{feed\_item.is\_blocked} from changed views. Rehearsal found it where coverage missed it. Both callers belong to one commit~\cite{feedview}. This prompted a retrospective rule: use native rehearsal if an old read belongs to a view whose stored definition changed or disappeared. Otherwise use Stars. Among 3,756 supported old names, seven selected rehearsal. Every added-field list matched full rehearsal. All 28 native error messages were lost. The two RSS readers supplied 149 of the 157 expansions, so we sought independent applications before treating this rule as generally useful.

\section{Prospective test on three new histories}
We published the \href{https://github.com/oraoraoraaa/least-privilege-lab/blob/8ac30a2/research/triage/PLAN.md}{replication plan} and implementation before scoring Phoenix (wallet), Press (notes), and Zipline (code cache). We selected the three for their domains and accessible production SQL. At their pinned heads through 2025 we identified the SQL directories of their production databases. Within those roots we followed the full first-parent history from first appearance. Earlier source layouts outside those roots are outside this frame. Repeated transitions come from the same projects and share schema edits. We report paired counts by project.

None of the 425 old names touched a view whose definition changed or disappeared. The fresh cohort therefore tests the wildcard fallback. It supplies no independent replication of the changed-view benefit. On 27 expansions the broad diff was exact 26 times with five extra query--field instances across supported survivors. Selective was exact 22 times and full rehearsal 18 times, each with zero extra instances. The four unequal field lists arose from three Press commits. For example, \code{Note.selectAll} kept a wildcard but its old ordering clause referenced a renamed column. SQLite reported the missing old name and returned no added fields. Stars correctly named all three replacement fields that the edited query read~\cite{press}. Full rehearsal supplied information that the correct forecast alone could not explain.

All 18 native errors also entered the selective review queue via other evidence. Twelve affected names later retired, five survived, and one had an unsupported next endpoint. The selective rule lost the reason SQLite supplied, even where the reviewer still saw the name. Six queue-membership decisions differed across all 425 comparisons. Ten of the 66 transitions had incomplete catalogs. Unsupported endpoints are retained in the ledger.

\paragraph{Elapsed time.} We timed actual predictor passes after loading old footprints and planned schemas, with one warmup and five alternating-order repetitions per transition. We cleared the wildcard parser cache before each pass. Across the 66 transitions, summing per-transition medians gave 4.1\,ms for native rehearsal and 80.9\,ms for selective on an Apple M4, and 6.6 and 100.3\,ms on an Arch Linux Ryzen 9 7945HX. Across the five repetitions, whole-cohort native totals ranged from 4.2 to 4.5\,ms on the Mac and 6.5 to 6.6\,ms on Arch. Selective totals ranged from 81.6 to 86.8 and 99.5 to 106.5\,ms, respectively. Both used SQLite 3.53.1. These are small local catalogs. We did not measure a persistent syntax cache, database construction, remote database latency, or human review time. Fewer native calls supplied no elapsed-time advantage in this setting.

\paragraph{Measure generated SQL when the build is available.} We invoked all ten named read methods from each of Zipline's published JVM artifacts 1.1.0 and 1.2.0. A recording SQLDelight driver intercepted each emitted SQL statement and its bound values. Two methods generate different SQL for null and non-null arguments. We exercised both shapes, yielding 12 executions per release. On the corresponding schema the compiled and source read sets matched on all 24 executions. The source grants admitted every compiled statement, and dropping each required grant in turn denied it. The two versions had identical SQL input files. This validates the release measurement on stable inputs. The Mihon witness supplies the separate example in which rebuilding actually changed the access requirement~\cite{zipline,mihon}.

\section{How often can the entire database upgrade?}
For a shared account we retain old grants that still exist, pool votes from all supported old queries, install the candidate on a database connection, and evaluate every next named read including introductions. Uncapped evidence policies add only forecast resources. Padded diff fills up to four slots using the frozen ordering and a deterministic digest tie break. A grant is unused if no next named read requests it. Each grant counts once per account and transition. Native admissions are checked against set containment.

In the original cohort, padding the diff made two further FeedFlow upgrades pass. Of 222 unused additions, 198 were table-only grants and 24 were named-column grants. SQLite requests a table-only read for statements such as \code{SELECT count(*) FROM t}. It can expose a count. Reading a notes column can expose text. The 24 named-column instances comprise just three distinct column identifiers repeated at different transitions. Treating every grant as equally sensitive would require a data-owner judgment.

\paragraph{Recovering search-heavy catalogs.} We extended the inventory to hidden full-text search (FTS) fields, callback-visible row identifiers and the read-only SQLite data-version check. FTS can prepare internal reads of shadow tables on first use and reuse those statements later. We create a fresh in-memory database for each distinct execution, recording those internal permissions. The populated fixture checks the FTS read under its observed policy and under policies missing a required resource. It also checks an ordinary implicit row identifier and a table defined without one. Main catalog executions use empty databases and fixed parameter shapes. Different data can exercise different engine internals.

All 103 previously incomplete Twine transitions and all 45 incomplete FeedFlow transitions became measurable. On these 148 upgrades, coverage and diff installed identical grants in every case. Padding admitted one further statement, completed one further upgrade, and left 548 unused additions. These comprised 186 hidden fields, 183 table-only grants, 176 row identifiers, two ordinary columns and one shadow-table column. The archive also reruns the 48 previously complete transitions from these two projects under the extended model. Expanding the available resource inventory can change a padded policy even on an unchanged catalog. The two blocks therefore retain their original measurement conditions.

\section{Who may receive the result?}
\paragraph{A recipient with an explicit choice.} Phoenix's merged export design specifies that recipients receive a subset of stored payment information~\cite{phoenix}. In the Android v2.6.2 source the user-facing switch sets the notes and description options together. The export view model calls \code{listCompletedPayments}, which invokes \code{Payments.listSuccessful}. That SQL selects the payment payload and all joined metadata. The released writer then chooses the description text sent to the recipient. We used the published switch and upstream test as the authorization evidence and evaluated the two reachable switch settings.

On a database populated with a synthetic completed payment, withholding the notes grant denied the internal query. Its observed grants admitted it and returned both fixture strings. We passed the returned strings to the exact description expression extracted from the tagged Kotlin writer, compiled with fixture input types. With the switch on, the expression emitted the description and note. With it off, the expression emitted an empty field. A reviewer who removed the internal grant to implement the recipient's choice would break the export. A reviewer who inferred recipient permission from the database read would approve the wrong output in the off state. The checked decision is a published maintainer choice at the output boundary. We exercised the SQL and the writer expression, without running the Android UI or eliciting a new maintainer decision.

\paragraph{Conclusion.} In these histories a broad diff anticipated most edited queries' new fields. Native rehearsal cheaply explained the behavior of the old program and identified stale SQL, including cases where a wildcard forecast correctly anticipated the developer's repair. When the replacement program was available, the emitted SQL settled its technical requirement directly. Whether a recipient should see a value depended on the application's caller and the user's choice. The evidence supports using different observations at those three review points. It supplies no estimate of production incidence or of how an alert changes human decisions.
