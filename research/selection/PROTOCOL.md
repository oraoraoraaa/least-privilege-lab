# Choosing a preflight before the next query arrives

This extension follows the first manuscript at 643d6bf. The primary benchmark results and their duplicate-footprint audit are known. The following design was fixed before running the selector comparison or collecting Tivi authorization traces. Reconnaissance established source availability, snapshot dates, file counts and the format of SQLDelight definitions.

## Two candidates on JOB and STATS

Enumerate every ordered observed and hidden pair with at least one new hidden read and every unordered pair of other candidate SQL IDs in its family. This requires at least four IDs. Compare the two native four-grant sibling policies already enforced for those candidates. The baseline is the original table/frequency policy. Choose one candidate by highest Jaccard similarity of the sets of identifier-like tokens in its SQL and the observed SQL. Strip comments and string literals, lowercase, retain SQL keywords and ignore numbers. Break ties by query ID. Evaluate the less similar candidate with the complementary tie choice, and compute uniform choice exactly by averaging the two decisions. The selector uses the two visible texts and the observation. Report all informative cases and repeat using one representative per unique footprint per family. Give families equal weight. Report where the closest choice improves or loses against random, with paired resampling of families as in the original paper.

Partition uniform selection failure into (1) more than four new required grants, (2) budget feasible but both candidates' policies fail, (3) one candidate succeeds and random choice misses it with probability one half. Also report success. These four quantities sum to one. The second term combines limitations of the available evidence and of its ranker. The best of two decisions uses hindsight solely to diagnose how much selection could improve with this particular ranking.

## Forward replay of an application

Use the archived public mainline of chrisbanes/tivi, an application using named SQLDelight queries. Take its last first-parent commit at each calendar quarter end after introduction of the SQL sources, then its archival head. Use each adjacent transition once. The seven source commits in chronological order are 2eaefa1ff0d0290320fcef43b09c5f031d1fbba3, 673cfdb7d19356d2fc919f25b0af683b9046537d, 92cd468cc7fc0c25d2b29ab61104ca7b22c0e0e4, fe251e72ca80d5b2451dc0773adf296304c2f29d, e7ff6c94209f78c79c5abd290b5e38e5c020a723, 2542f0087ca2c39920b086196607086c1ced6a10 and a0c62c2c763c83e3a0ecf79b283224374bb06c4a. Match a query across adjacent snapshots by SQL file stem and declared query name. Identify additions and departures separately. Include every named SELECT or read-only WITH statement, including ones with empty footprints. List normalization and any unsupported statements.

Use empty databases built from each snapshot's published table, index and view definitions. Strip Kotlin type adapters, bind harmless representative argument values and use a one-element list for collection parameters. Record native read callbacks on schema tables and views including underlying table reads, and verify policy decisions by native preparation. Each named read query is weighted once per adjacent transition. Report both total counts and a breakdown by transition. This is a historical replay of versioned statements, without user data or telemetry.

Each surviving query has an old observation O. Other old queries in the same source file form its named candidate pool. Select the nearest SQL text using the benchmark selector. Rank candidates from the old schema only and fix four grants as in the first paper. The baseline uses table/frequency counts from other old files, leaving the target file out. When no sibling exists, fall back to the baseline. Compare observed-only, baseline, closest and the exact average over a uniform old same-file candidate. Record the best possible same-file donor for diagnosis. Count cases where the old policy already covers the new query, required resources absent from the old schema, more than four old-schema additions required, and remaining feasible informative cases. Use mutually exclusive attribution in that order. Newly introduced IDs have no previous same-name observation and stay visible in the coverage denominator. Report native outcomes on surviving queries, including fallbacks. A new name does not imply a new workload or a rename. Keep application results separate from benchmark family averages. Report even a zero usable event count as a finding about this application's drift.

### Schema-change mechanism

Before collecting traces, add one diagnostic and a second operational setting. For each surviving name, compile its old query text against the next schema before reading the next query text. Record the newly required reads this rehearsal predicts and whether the old query still prepares. A team with migration DDL in hand can use this evidence. Compare the next-schema table/frequency policy with the same policy prioritizing the rehearsal reads, both preserving surviving O grants and adding four. Also score the literal union of surviving O and rehearsal reads with its actual cost. On preparation failure, use baseline rankings and record the reason. Distinguish unchanged normalized statement text from changed text, and report the new-column/read witnesses. Known DDL is an extra input and has its own comparator.
