# Checks motivated by the forward replay

The seven quarterly Tivi snapshots produced 516 surviving-name opportunities, zero expansions and eight introductions. These outcomes motivated the following tests. Commit the design before computing these outcomes. Report both applications regardless of direction.

1. Recheck the same Tivi date window at every first-parent commit changing an in-scope SQLDelight source. Start from the registered June 2023 snapshot and include the final archival snapshot only if its SQL sources differ. Count changed names, footprint expansions, introductions and departures, and preserve their identities. This checks whether quarterly endpoints mask transient changes.
2. For each new name at a transition, measure whether its next footprint is covered by any old query in the same file, the union of old queries in its file, the old application-wide union, and the old schema. Record the missing resources for each and whether the file existed. These nested hindsight coverage tests diagnose missing evidence. They do not prescribe granting every old read.
3. Replicate the complete forward policy comparison on a second open-source SQLite application, Mihon. Use the first six consecutive minor-version tags from v0.16.0 through v0.21.0 (peeled commits a605a4ec7572919f8c6ad599dce677dd648ca2ad, 38d5fc91606f28287827bc53ee1410d8ab54bf9f, 6294521460a8eb8b755b7a8c3c07d4bfa2e9a9e0, e4de208cf75e273b425bf4b1fe4bd7bc3d9cc459, 19f1d00fcbef6ab7783066ff9ae8e377f696b231 and 79fc3a0a8aaa6cd2b6dc21c3f8ee53f008da654a). Include all application SQLDelight table and view source files. Apply the same projections, all named reads, unit of analysis, four-grant limit and preflight rules without tuning. Record syntactic adaptations, unsupported reads and all denominators. Check the old SQL on new DDL as above. Use SCM history and published program source, and never infer production query frequency from it.

### Interpreting the release result

Mihon had 49 expansions, all involving a resource outside the older schema, and 40 had identical normalized SQL. SQLDelight's release notes describe expanding wildcard projections during code generation. To check the distinction between old source and a shipped old literal, inspect the official x86-64 APK assets for v0.18.0 and v0.19.0. Use the previously observed, unchanged query mangas.getMangaById, whose expanded source reads gained mangas.notes. Identify static SQL strings by their direct lookup of mangas by _id and either a wildcard or the complete projected column list of that tag. Report missing or ambiguous matches. Prepare each unique matching literal against its own schema and the old literal against the next schema. This is a single-case validation of embedded query text.

Measure a review signal available before reading next-version queries. Flag a surviving name if its old source fails to prepare on the planned schema or asks for a new read there. Compare the flag to actual held-out footprint expansion. Archive the confusion counts, including the no-expansion Tivi case. Report the costs in additional and unused grants of literal rehearsal and four-grant policies. In the benchmark selector, also average the choices on exactly tied similarity to isolate dependence on identifier ordering. These targeted follow-ups were chosen after the main results.

The first diagnostic scored surviving names. A reviewer sees the entire old catalog and cannot know which names will disappear. Also report the count of flagged retired names, total flags per transition, and new names outside the tool's reach. Preserve these counts in the paper and provide a report generator that reads only the older queries and the planned schema.
